# Деплой

Всё, что нужно сделать человеку — добавить два секрета в GitHub. Установку
Node, pm2, nginx, выпуск HTTPS-сертификата, раскладку файлов, перезапуск и
настройку кнопки бота деплой делает сам.

## 1. Секреты в GitHub

Вся конфигурация деплоя живёт **только** в секретах Actions. В репозитории
никаких значений нет и быть не должно: `.env` для сервера собирается на
раннере из этих секретов при каждом деплое. Файл `server/.env.example`
нужен исключительно для локальной разработки и на сервер не попадает.

`Settings → Secrets and variables → Actions → New repository secret`

### Обязательные

| Имя | Что это |
|---|---|
| `SSH_HOST` | IP сервера (или домен, если есть) |
| `SSH_PASSWORD` | пароль от SSH — **либо** вместо него `SSH_PRIVATE_KEY` (приватный ключ целиком, вместе со строками `-----BEGIN...`/`-----END...`) |

Пароль и ключ взаимозаменяемы: задан пароль — деплой заходит по паролю
(через `sshpass`, пароль передаётся переменной окружения, а не аргументом
командной строки, чтобы не светиться в списке процессов); задан ключ —
по ключу. Если заданы оба, используется пароль.

### Остальные

| Имя | По умолчанию | Когда задавать |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | токен бота от @BotFather (см. ниже) |
| `SSH_USER` | `root` | если заходите под другим пользователем (нужен passwordless sudo) |
| `SSH_PORT` | `22` | если SSH на другом порту |
| `DEPLOY_PATH` | `/opt/system-dynamics-ui` | если нужен другой каталог |
| `APP_DOMAIN` | `<ip>.sslip.io` | если есть свой домен, направленный на этот сервер |

### Напоминания о задачах

Планировщик живёт на сервере (`server/src/lib/scheduler.js`) и раз в минуту
проверяет расписания всех пользователей. Присылает два вида сообщений:
предупреждение за выбранное в задаче время и уведомление в момент начала.

Что нужно, чтобы работало:

1. **`TELEGRAM_BOT_TOKEN`** — без него планировщик не запускается вовсе
   (слать нечем), о чём сервер пишет в лог при старте.
2. **Пользователь должен начать диалог с ботом.** Telegram запрещает боту
   писать первым: если диалога не было, API отвечает 403, и напоминание не
   дойдёт. В интерфейсе про это написано под полем «Предупредить».
3. **`SCHEDULES_DIR`** — задаётся деплоем автоматически
   (`${DEPLOY_PATH}/data/schedules`). Важно, что это **вне** каталога
   `app/`: он стирается `rsync --delete` при каждом деплое. То же относится
   к `SCENARIOS_DIR` и `REPORTS_DIR`.

Расписание уезжает на сервер само, через секунду после правки задач.
Проверить, что оно дошло: `ls ${DEPLOY_PATH}/data/schedules` — там по файлу
на пользователя. Логи планировщика видны в `pm2 logs system-dynamics-ui`
с префиксом `[scheduler]`.

### Что даёт `TELEGRAM_BOT_TOKEN`

Токен нужен серверу, чтобы проверять подпись `Telegram.WebApp.initData`:
без этой проверки нельзя открывать API записи на диск — писать в него смог
бы любой желающий. Поэтому поведение зависит от того, задан ли он:

- **задан** → сценарии сохраняются файлами на диске сервера
  (`${DEPLOY_PATH}/data/scenarios/<id пользователя>/`), файлы отчётов — там
  же (`${DEPLOY_PATH}/data/reports/`), и деплой сам привязывает WebApp к
  кнопке бота через `setChatMenuButton`;
- **не задан** → `/api/health` отдаёт `scenarios: false` и `reports: false`,
  фронтенд это видит и сохраняет сценарии в облако Telegram (CloudStorage —
  привязано к аккаунту, доступно со всех устройств), а файлы отчётов кладёт
  внутрь сценария как `data:`-URL, не больше 2 МБ. Приложение полностью
  рабочее, но кнопку бота придётся назначить руками в @BotFather.

Деплой из-за отсутствия токена не падает — это осознанный выбор, чтобы
приложение можно было поднять и проверить до того, как заведён бот.

## 2. Запуск

После добавления секретов: **Actions → CI/CD → Run workflow → ветка `main`**.
Пустой коммит не нужен. Дальше деплой идёт сам на каждый push в `main`.

## 3. Что именно делает деплой

1. **Тесты и сборка** — vitest для `web/` и `server/`, репетиция скриптов
   деплоя в песочнице, `vite build`.
2. **Подготовка сервера** (`deploy/bootstrap.sh`, идемпотентно):
   ставит `rsync`, `curl`, `nginx`, `certbot`, Node.js 20 и `pm2` — если
   чего-то нет; создаёт каталоги; настраивает nginx-прокси на порт 3000;
   выпускает сертификат Let's Encrypt; включает автозапуск после
   перезагрузки сервера. Скрипт уходит на сервер по stdin, поэтому на нём
   заранее не нужно вообще ничего.
3. **Раскладка** — `rsync --delete` в `${DEPLOY_PATH}/app`. Каталог с
   данными лежит рядом (`${DEPLOY_PATH}/data`), поэтому сохранённые
   сценарии переживают любой деплой.
4. **Запуск** (`deploy/release.sh`) — `npm ci --omit=dev`,
   `pm2 startOrReload`, затем health-check: если приложение не ответило за
   30 секунд, деплой падает и печатает последние 50 строк логов pm2.
5. **Проверка снаружи** — `https://<домен>/api/health`.
6. **Кнопка бота** — если задан `TELEGRAM_BOT_TOKEN`, вызывается
   `setChatMenuButton`, и WebApp появляется у бота рядом с полем ввода.

Итоговый адрес приложения пишется в summary прогона.

## 4. HTTPS без своего домена

Telegram требует HTTPS с доверенным сертификатом. Домен покупать не нужно:
используется [sslip.io](https://sslip.io) — публичный DNS, где имя вида
`203-0-113-42.sslip.io` резолвится в IP `203.0.113.42`. Имя реально
резолвится, поэтому Let's Encrypt спокойно выдаёт на него сертификат.
Домен вычисляется из `SSH_HOST` автоматически.

Если появится свой домен — направьте его на сервер и задайте секрет
`APP_DOMAIN`; код менять не нужно.

## 5. Если что-то пошло не так

Ошибки сформулированы человеческим языком прямо в логе прогона:

| Сообщение | Что делать |
|---|---|
| `Permission denied (publickey,password)` | неверный `SSH_PASSWORD`/`SSH_PRIVATE_KEY` или `SSH_USER` |
| `нужен root или passwordless sudo` | задать `SSH_USER=root` или разрешить пользователю sudo без пароля |
| `не удалось выпустить сертификат` | открыть порт 80 в firewall хостера (Let's Encrypt проверяет домен по нему) |
| `HTTPS снаружи не отвечает` | открыть порт 443 в firewall хостера |
| `/api/health не ответил за 30 секунд` | ниже в логе — 50 строк логов pm2 с причиной падения |

## 6. Локальная разработка

```bash
npm run install:all
npm run dev:server    # backend на :3000
npm run dev:web        # frontend на :5173, /api проксируется на :3000
```

Вне Telegram приложение работает как обычная страница: `Telegram.WebApp`
отсутствует, сценарии сохраняются в localStorage браузера.

## 6.5. Владелец, роли и приглашение людей

Модель одна на всех, и принадлежит она **владельцу**. Владелец — единственный,
кто видит все задачи, правит структуру системы и зовёт людей.

**Как назначается владелец.** Надёжный способ — секрет Actions
`OWNER_TELEGRAM_ID` с вашим числовым id Telegram (узнать его можно, отправив
боту `/id`). Он попадает в `.env` при деплое, и с этого момента владелец
зафиксирован.

Если секрет не задан, владельцем становится **первый, кто открыл приложение**.
На публичном адресе так делать не стоит: первым может оказаться не тот, а
переиграть это можно будет только задав `OWNER_TELEGRAM_ID` и передеплоив.

**Как позвать человека.** Владелец пересылает боту сообщение от нужного
человека — бот показывает роли кнопками, владелец выбирает одну или заводит
новую названием. Всё, что бот получает не от владельца, он отклоняет.

Тонкость Telegram: если у человека в настройках приватности закрыт перенос
сообщений, `forward_from` не приходит и id узнать неоткуда. Бот об этом
скажет; тогда пусть человек отправит боту `/id` и пришлёт вам номер, а вы
отправите боту `id 123456789 Имя`.

**Роли** — это наборы вкладок. Встроенные: «исполнитель» (Задачи),
«проверяющий» (Проверка), «исполнитель и проверяющий». Новая роль из бота
открывает только «Задачи»; остальное настраивается в приложении, на вкладке
«Выгрузить», в панели «люди и роли» (её видит только владелец).

Всё это держится на подписи Telegram: без `TELEGRAM_BOT_TOKEN` отличить
владельца от кого угодно нечем, поэтому `/api/health` отдаёт `org: false`, а
приложение работает как одиночное — модель в браузере, и владелец в ней сам
пользователь.

## 6.6. Звонки

Созвон идёт внутри мини-приложения: видео и звук — напрямую между
собеседниками, сервер только сводит их.

**Что нужно включить руками:**

1. **Инлайн-режим бота** — `/setinline` в @BotFather. Без него Telegram не
   пришлёт инлайн-запросов, и позвать карточкой «@бот завтра 15:00 разбор»
   не получится (внутри приложения встречи всё равно работают).
2. **`TELEGRAM_APP_NAME`** — короткое имя мини-приложения из BotFather
   (Bot Settings → Menu Button → Configure Mini App). Из него собирается
   ссылка `t.me/<бот>/<приложение>?startapp=call_<id>`; без него ссылка
   будет вести на домен напрямую, что тоже работает, но открывается в
   браузере, а не в Telegram.
3. **TURN — по желанию, но честно:** `TURN_URL`, `TURN_USER`, `TURN_PASS`.
   Публичного STUN хватает в большинстве сетей, но если **оба** собеседника
   за строгим NAT, соединение без TURN не установится вовсе. Приложение в
   этом случае так и говорит. Бесплатного публичного TURN не бывает — это
   либо свой coturn на этом же сервере, либо услуга.

Камеру и микрофон спрашивает сам Telegram. На части клиентов (особенно
старых iOS) доступ к камере из мини-приложения может быть недоступен —
тогда приложение скажет об этом словами, а не покажет чёрный экран.

## 6.7. Мост к Claude Code

Бот умеет передать вопрос в ваш Claude Code и вернуть ответ. Ключ API не
нужен: Claude Code работает под вашей же подпиской, на вашей машине.

Устроено очередью: сервер кладёт вопрос, **воркер на вашей машине** его
забирает. Так сделано не из осторожности, а потому что иначе не работает —
вход в Claude Code интерактивный и привязан к аккаунту, на VPS его не
перенести. Побочные выгоды: сервер ничего не исполняет, и дома не нужно
открывать ни одного порта.

**Настройка:**

1. Придумайте секрет — **только латиница и цифры**, не короче 8 символов
   (заголовки HTTP не несут кириллицу, и с русским секретом воркер просто
   не подключится).
2. Положите его в секреты Actions как `BRIDGE_TOKEN` и передеплойте.
3. На своей машине, где `claude` уже вошёл в аккаунт:

```
BRIDGE_URL=https://ваш-домен \
BRIDGE_TOKEN=тот-же-секрет \
BRIDGE_CWD=/путь/к/репозиторию \
node tools/claude-bridge.mjs
```

4. В боте: `/claude что в логах?` — или `/claude` без текста, чтобы каждое
   следующее сообщение уходило в мост, и `/stop`, чтобы выйти.

**Права.** Воркер запускает Claude Code с теми правами, что есть у вас, в
каталоге `BRIDGE_CWD`. По умолчанию разрешены только чтение и поиск
(`BRIDGE_TOOLS=Read,Grep,Glob`). Расширять — осознанное решение: спросить
«можно?» в чате будет некому. Режим «делать что угодно без вопросов» здесь
не выставляется вовсе.

**Кому доступно:** только владельцу. Мост выключен целиком, пока не задан
`BRIDGE_TOKEN`.

## 7. Где лежат сценарии и файлы отчётов

```
${DEPLOY_PATH}/data/scenarios/<telegram_user_id>/manifest.json   — список сценариев
${DEPLOY_PATH}/data/scenarios/<telegram_user_id>/<uuid>.json     — сами сценарии
${DEPLOY_PATH}/data/reports/users/<telegram_user_id>             — указатель на scope
${DEPLOY_PATH}/data/reports/<scope>/manifest.json                — список файлов
${DEPLOY_PATH}/data/reports/<scope>/<uuid>                       — сами файлы
${DEPLOY_PATH}/data/org/org.json                                 — владелец, роли, люди
${DEPLOY_PATH}/data/workspace/model.json                         — общая модель
${DEPLOY_PATH}/data/calls/meetings.json                          — встречи
```

Комнаты созвонов на диск не пишутся вовсе: сигналы живут в памяти и
стираются через десять минут после звонка — в них адреса участников.

Имена файлов — сгенерированные сервером UUID, поэтому произвольный ввод в
URL не даёт доступа за пределы каталога пользователя.

Каталог отчётов назван не id пользователя, а случайным 32-символьным
`scope`, потому что ссылка на файл должна открываться браузером напрямую:
`<img src>` и обычная ссылка не могут подставить заголовок с подписью
Telegram. Знание пары `scope`+`id` и есть право на чтение — **у кого ссылка,
тот и прочитает файл**, а значит, отдать сценарий целиком значит отдать и
его отчёты. Загрузка и удаление подпись по-прежнему требуют. Указатель
`users/<id>` выдаётся один раз и от токена бота не зависит: сменится бот —
ссылки в уже сохранённых сценариях продолжат работать.

Каталог `data/` лежит **вне** `app/`, который стирается `rsync --delete`
при каждом деплое, поэтому обновление приложения файлы не трогает.
