# Деплой

Всё, что нужно сделать человеку — добавить два секрета в GitHub. Установку
Node, pm2, nginx, выпуск HTTPS-сертификата, раскладку файлов, перезапуск и
настройку кнопки бота деплой делает сам.

## 1. Секреты в GitHub

Вся конфигурация деплоя живёт **только** в секретах Actions. В репозитории
никаких значений нет и быть не должно: `.env` для сервера собирается на
раннере из этих секретов при каждом деплое. Файл `server/.env.example`
нужен исключительно для локальной разработки и на сервер не попадает.

`Settings → Secrets and variables → Actions → New repository secret`

### Обязательные

| Имя | Что это |
|---|---|
| `SSH_HOST` | IP сервера (или домен, если есть) |
| `SSH_PASSWORD` | пароль от SSH — **либо** вместо него `SSH_PRIVATE_KEY` (приватный ключ целиком, вместе со строками `-----BEGIN...`/`-----END...`) |

Пароль и ключ взаимозаменяемы: задан пароль — деплой заходит по паролю
(через `sshpass`, пароль передаётся переменной окружения, а не аргументом
командной строки, чтобы не светиться в списке процессов); задан ключ —
по ключу. Если заданы оба, используется пароль.

### Остальные

| Имя | По умолчанию | Когда задавать |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | токен бота от @BotFather (см. ниже) |
| `SSH_USER` | `root` | если заходите под другим пользователем (нужен passwordless sudo) |
| `SSH_PORT` | `22` | если SSH на другом порту |
| `DEPLOY_PATH` | `/opt/system-dynamics-ui` | если нужен другой каталог |
| `APP_DOMAIN` | `<ip>.sslip.io` | если есть свой домен, направленный на этот сервер |
| `OWNER_TELEGRAM_ID` | первый вошедший | чтобы владельцем стал именно этот аккаунт (см. 6.5) |
| `TELEGRAM_CALL_APP` | задаётся из чата | короткое имя отдельного мини-приложения звонка из `/newapp` (см. 6.6). Проще сообщить его боту командой `/callapp call` — сервер сохранит сам |
| `TELEGRAM_CALL_MAIN` | задаётся из чата | `1` — открывать звонок главным приложением бота, ради окна на пол-экрана (см. 6.6). Ставится командой `/callmain on`, снимается `/callmain off`; секрета для неё нет — значение живёт на сервере, деплой его сохраняет |
| `TURN_SECRET` | рождается деплоем | задавать не нужно: деплой создаёт его сам и сохраняет между обновлениями |
| `ASSISTANT_DIR`, `CHATS_DIR` | `data/assistant`, `data/chats` | каталог с провайдерами, ключами и моделями каждого человека (файл на пользователя, права 0600) и каталог сообщений групп. Прежние `AI_PROVIDER`/`AI_MODEL`/`*_API_KEY` из `.env` переносятся владельцу один раз и больше не читаются |
| `MARKET_DIR`, `ISSUES_DIR` | `data/market`, `data/issues` | заказы и услуги рынка; сообщения об ошибках, присланные значком в шапке. Оба каталога обязаны лежать в `data/`: `app/` переписывается каждым деплоем (`rsync --delete`), и умолчание рядом с кодом означало бы потерю записей при каждом обновлении |
| `UNDO_DIR` | `data/undo` | что откатывает кнопка «Отменить изменения» под подтверждённым изменением помощника. Срока у неё нет, поэтому запись обязана пережить деплой — и лежать в `data/` |

### Напоминания о задачах

Планировщик живёт на сервере (`server/src/lib/scheduler.js`) и раз в минуту
проверяет расписания всех пользователей. Присылает два вида сообщений:
предупреждение за выбранное в задаче время и уведомление в момент начала.

Что нужно, чтобы работало:

1. **`TELEGRAM_BOT_TOKEN`** — без него планировщик не запускается вовсе
   (слать нечем), о чём сервер пишет в лог при старте.
2. **Пользователь должен начать диалог с ботом.** Telegram запрещает боту
   писать первым: если диалога не было, API отвечает 403, и напоминание не
   дойдёт. В интерфейсе про это написано под полем «Предупредить».
3. **`SCHEDULES_DIR`** — задаётся деплоем автоматически
   (`${DEPLOY_PATH}/data/schedules`). Важно, что это **вне** каталога
   `app/`: он стирается `rsync --delete` при каждом деплое. То же относится
   к `SCENARIOS_DIR`, `REPORTS_DIR` и `SHARES_DIR` (снимки блоков карты
   отчётов, которые открываются по общей ссылке).

Расписание уезжает на сервер само, через секунду после правки задач.
Проверить, что оно дошло: `ls ${DEPLOY_PATH}/data/schedules` — там по файлу
на пользователя. Логи планировщика видны в `pm2 logs system-dynamics-ui`
с префиксом `[scheduler]`.

### Что даёт `TELEGRAM_BOT_TOKEN`

Токен нужен серверу, чтобы проверять подпись `Telegram.WebApp.initData`:
без этой проверки нельзя открывать API записи на диск — писать в него смог
бы любой желающий. Поэтому поведение зависит от того, задан ли он:

- **задан** → сценарии сохраняются файлами на диске сервера
  (`${DEPLOY_PATH}/data/scenarios/<id пользователя>/`), файлы отчётов — там
  же (`${DEPLOY_PATH}/data/reports/`), и деплой сам привязывает WebApp к
  кнопке бота через `setChatMenuButton`;
- **не задан** → `/api/health` отдаёт `scenarios: false` и `reports: false`,
  фронтенд это видит и сохраняет сценарии в облако Telegram (CloudStorage —
  привязано к аккаунту, доступно со всех устройств), а файлы отчётов кладёт
  внутрь сценария как `data:`-URL, не больше 2 МБ. Приложение полностью
  рабочее, но кнопку бота придётся назначить руками в @BotFather.

Деплой из-за отсутствия токена не падает — это осознанный выбор, чтобы
приложение можно было поднять и проверить до того, как заведён бот.

## 2. Запуск

После добавления секретов: **Actions → CI/CD → Run workflow → ветка `main`**.
Пустой коммит не нужен. Дальше деплой идёт сам на каждый push в `main`.

## 3. Что именно делает деплой

1. **Тесты и сборка** — vitest для `web/` и `server/`, репетиция скриптов
   деплоя в песочнице, `vite build`.
2. **Подготовка сервера** (`deploy/bootstrap.sh`, идемпотентно):
   ставит `rsync`, `curl`, `nginx`, `certbot`, Node.js 20 и `pm2` — если
   чего-то нет; создаёт каталоги; настраивает nginx-прокси на порт 3000;
   выпускает сертификат Let's Encrypt; включает автозапуск после
   перезагрузки сервера. Скрипт уходит на сервер по stdin, поэтому на нём
   заранее не нужно вообще ничего.
3. **Раскладка** — `rsync --delete` в `${DEPLOY_PATH}/app`. Каталог с
   данными лежит рядом (`${DEPLOY_PATH}/data`), поэтому сохранённые
   сценарии переживают любой деплой.
4. **Запуск** (`deploy/release.sh`) — `npm ci --omit=dev`,
   `pm2 startOrReload`, затем health-check: если приложение не ответило за
   30 секунд, деплой падает и печатает последние 50 строк логов pm2.
5. **Проверка снаружи** — `https://<домен>/api/health`.
6. **Кнопка бота** — если задан `TELEGRAM_BOT_TOKEN`, вызывается
   `setChatMenuButton`, и WebApp появляется у бота рядом с полем ввода.

Итоговый адрес приложения пишется в summary прогона.

## 4. HTTPS без своего домена

Telegram требует HTTPS с доверенным сертификатом. Домен покупать не нужно:
используется [sslip.io](https://sslip.io) — публичный DNS, где имя вида
`203-0-113-42.sslip.io` резолвится в IP `203.0.113.42`. Имя реально
резолвится, поэтому Let's Encrypt спокойно выдаёт на него сертификат.
Домен вычисляется из `SSH_HOST` автоматически.

Если появится свой домен — направьте его на сервер и задайте секрет
`APP_DOMAIN`; код менять не нужно.

## 5. Если что-то пошло не так

Ошибки сформулированы человеческим языком прямо в логе прогона:

| Сообщение | Что делать |
|---|---|
| `Permission denied (publickey,password)` | неверный `SSH_PASSWORD`/`SSH_PRIVATE_KEY` или `SSH_USER` |
| `нужен root или passwordless sudo` | задать `SSH_USER=root` или разрешить пользователю sudo без пароля |
| `не удалось выпустить сертификат` | открыть порт 80 в firewall хостера (Let's Encrypt проверяет домен по нему) |
| `HTTPS снаружи не отвечает` | открыть порт 443 в firewall хостера |
| `/api/health не ответил за 30 секунд` | ниже в логе — 50 строк логов pm2 с причиной падения |

## 6. Локальная разработка

```bash
npm run install:all
npm run dev:server    # backend на :3000
npm run dev:web        # frontend на :5173, /api проксируется на :3000
```

Вне Telegram приложение работает как обычная страница: `Telegram.WebApp`
отсутствует, сценарии сохраняются в localStorage браузера.

## 6.5. Владелец, роли и приглашение людей

Модель одна на всех, и принадлежит она **владельцу**. Владелец — единственный,
кто видит все задачи, правит структуру системы и зовёт людей.

**Как назначается владелец.** Надёжный способ — секрет Actions
`OWNER_TELEGRAM_ID` с вашим числовым id Telegram (узнать его можно, отправив
боту `/id`). Он попадает в `.env` при деплое, и с этого момента владелец
зафиксирован.

Если секрет не задан, владельцем становится **первый, кто открыл приложение**.
На публичном адресе так делать не стоит: первым может оказаться не тот, а
переиграть это можно будет только задав `OWNER_TELEGRAM_ID` и передеплоив.

**Как позвать человека.** Владелец пересылает боту сообщение от нужного
человека — бот показывает роли кнопками, владелец выбирает одну или заводит
новую названием. Всё, что бот получает не от владельца, он отклоняет.

Тонкость Telegram: если у человека в настройках приватности закрыт перенос
сообщений, `forward_from` не приходит и id узнать неоткуда. Бот об этом
скажет; тогда пусть человек отправит боту `/id` и пришлёт вам номер, а вы
отправите боту `id 123456789 Имя`.

**Роли** — это наборы вкладок. Встроенные: «исполнитель» (Задачи),
«проверяющий» (Проверка), «исполнитель и проверяющий». Новая роль из бота
открывает только «Задачи»; остальное настраивается в приложении, на вкладке
«Выгрузить», в панели «люди и роли» (её видит только владелец).

Всё это держится на подписи Telegram: без `TELEGRAM_BOT_TOKEN` отличить
владельца от кого угодно нечем, поэтому `/api/health` отдаёт `org: false`, а
приложение работает как одиночное — модель в браузере, и владелец в ней сам
пользователь.

## 6.55. Место на диске

Диск маленького VPS заполняется не приложением, а тем, что растёт само:
логами pm2, кэшами apt и npm, системным журналом. Записи созвонов добавились
к этому сверху — одна может весить до 100 МБ.

**Уборка идёт на каждом деплое** (`deploy/cleanup.sh`, шаг «Освободить место
на сервере»). Она чистит кэш apt и ненужные пакеты, обрезает системный журнал
до 100 МБ и ставит ему потолок на будущее, очищает логи pm2 и заводит им
ротацию (не больше 20 МБ), очищает кэши сборки и временные файлы старше
недели. В логе шага видно «было / стало / освобождено».

**Данные она не трогает никогда.** Всё внутри `${DEPLOY_PATH}/data` —
сценарии, файлы отчётов, записи созвонов, роли, общая модель — только
измеряется: шаг печатает размер каждого подкаталога (в том числе сообщений
групп `chats` — единственного, что растёт без срока, — и файлов ключей
`assistant`) и число записей созвонов.
Удалять это — решение владельца, и делается оно вручную:

```
rm ${DEPLOY_PATH}/data/reports/<имя файла>
```

Если после уборки занято больше 90 %, шаг об этом прямо предупреждает: дальше
освобождать можно только за счёт данных или расширением диска у хостера.

## 6.6. Звонки

Звонок — **отдельное окно**, а не вкладка модели: страница `https://<домен>/call`
со своим входом. Открывается из приглашения в чате на **пол-экрана**
(Telegram, режим `compact`); на весь экран человек тянет его сам или жмёт «⤢».
Всё окно помещается в экран телефона без прокрутки: сетка видео растягивается,
кнопки внизу.

**Медиа идёт только через сервер.** Каждый участник соединён с каждым, но
звук и видео всегда ретранслирует coturn на этом же сервере
(`iceTransportPolicy: relay`) — прямых путей между телефонами нет. Один
механизм и для двоих, и для десяти; «с одним соединилось, с другим нет из-за
NAT» больше не бывает: путь до сервера у всех один. Без TURN звонок не
начинается — окно так и говорит.

Предел комнаты — 20 человек. Каждый отдаёт по потоку на каждого другого; на
телефоне после пятерых частота кадров падает. Следующий шаг — сервер-микшер
(SFU), который берёт один поток и раздаёт всем; он в роадмапе.

**Звонок отдельно от модели.** Ссылка из приглашения ведёт в **отдельное**
мини-приложение звонка и никогда — в приложение модели. Ссылки вида
`t.me/<бот>?startapp=…` (главное мини-приложение) здесь больше нет вовсе:
во-первых, звонок не должен открываться внутри модели; во-вторых, такая ссылка
**молча** превращается в ссылку на чат с ботом, если главное мини-приложение не
заведено в @BotFather, — то есть по ней не открывается ничего.

**Войти по ссылке может любой, кому она попала** — регистрация в боте не нужна,
Telegram не обязателен. Право войти даёт знание неугадываемого id встречи, как
и у файлов отчётов. Что при этом закрыто: заводить встречи, видеть их список и
удалять могут только те, кого позвали в модель. Номеров Telegram участники друг
о друге не узнают — внутри комнаты у каждого псевдоним.

**Что настраивается руками в @BotFather:**

1. **Инлайн-режим** — `/setinline`. Без него бот не получит инлайн-запросов, и
   позвать карточкой «@бот завтра 15:00 разбор» не выйдет.
2. **Отдельное приложение звонка** — `/newapp`, выберите бота, название
   «Звонок», описание, картинку 640×360, адрес **`https://<домен>/call`**,
   короткое имя, например `call`.

   > **Адрес — доменом, а не IP.** `https://144.124.240.20/call` не
   > заработает: сертификат выписан на `144-124-240-20.sslip.io`, по IP имя
   > не совпадает, и Telegram молча показывает пустое окно — до HTTP дело не
   > доходит, поэтому и в журналах сервера пусто. Проверить адрес можно в
   > `/myapps` → приложение → `Edit Web App URL`; убедиться, что запросы
   > доходят, — по `callPage` в `/api/health`. Затем отправьте боту `/callapp call` — он
   запомнит имя в `.env`, деплой его сохранит, и ссылки станут вида
   `t.me/<бот>/call?startapp=call_…`. (Через Bot API такое приложение завести
   нельзя: метода нет, только @BotFather. Имя можно задать и секретом
   репозитория `TELEGRAM_CALL_APP` — это то же самое.)
3. **Главное мини-приложение бота** — Bot Settings → Configure Mini App. Раньше
   сюда полагалось записать адрес модели; теперь у этой строки появился выбор,
   и он про высоту окна звонка (см. врезку ниже). Модель от этой строки не
   зависит: она открывается кнопкой меню бота, а её адрес прописывает деплой.

   > **Если звонок открывается на весь экран, а хочется на половину.**
   >
   > **На компьютере половины нет вовсе** — ни у какого мини-приложения и ни
   > по какой ссылке. Telegram Desktop разбирает `fullsize` из ответа сервера
   > (`bot_attach_web_view.cpp:833`) и больше нигде это поле не читает: в
   > панель уходит одно `.fullscreen` (`:1476`), а у `Ui::BotWebView::Args`
   > полей compact/fullsize нет. Полуэкранного состояния в десктопном
   > интерфейсе не существует; окно там тянется мышью — это весь доступный
   > размер. (Для приложения из `/newapp` флаг compact вдобавок не
   > отправляется: в `local_url_handlers.cpp` условие начинается с
   > `appname.isEmpty()`, а в `requestApp()` флага `f_compact` нет — он есть
   > только в `requestMain()`.)
   >
   > **На телефоне** высоту решает ответ Telegram, а не ссылка: в
   > `BotWebViewSheet.isFullSize()` локальное намерение перезаписано полем
   > `fullsize` из ответа — отсюда открытая ошибка bugs.telegram.org/c/45743
   > и незакрытый PR DrKLO/Telegram#1930. Значит `mode=compact` у приложения
   > из `/newapp` не сработает и здесь. Но раз слушается ответ сервера,
   > остаётся рычаг, которым он задаётся: настройка высоты у ГЛАВНОГО
   > приложения. Запишите ему тот же адрес `https://<домен>/call`, выберите
   > там половину экрана и отправьте боту `/callmain on` — он проверит у
   > Telegram (`getMe` → `has_main_web_app`), что приложение заведено, и
   > переключит приглашения на `t.me/<бот>?startapp=call_…&mode=compact`.
   >
   > Убедиться, что записан правильный адрес, можно только глазами: адрес
   > приложения Bot API не сообщает никаким методом. `t.me/<бот>?startapp=check`
   > должен открыть тёмную страницу со словами «Ссылка на звонок неполная» —
   > это и есть окно звонка. Открылась модель — адрес не тот. Вернуть всё
   > назад: `/callmain off`.
   >
   > Свернуть окно из самой страницы нельзя ни на чём: `expand()`
   > односторонний, метода «свернуть» в Mini Apps нет — высота решается один
   > раз, при открытии. И ещё две ловушки проверки: свёрнутое окно
   > мини-приложения Telegram открывает в той же высоте, в какой его
   > оставили (закройте его полностью), а вход в звонок с вкладки «Звонки»
   > внутри модели идёт в окне модели — а его разворачивает наш же код.

**Пока приложение звонка не заведено**, ссылка ведёт на страницу
`https://<домен>/call?call=…`. Она открывается у всех, но обычной страницей: в
Telegram — встроенным браузером, а камеру и микрофон он даёт не везде (особенно
на iOS). Поэтому шаг 2 стоит сделать; деплой напоминает о нём в итоге запуска.

**Трансляция экрана** — кнопка «🖥» появляется там, где браузер это умеет:
на компьютере (Telegram Desktop, браузер). На телефонах Telegram не даёт
мини-приложению доступ к экрану — ни iOS, ни Android; кнопки там нет, а не
«не работает». Экран заменяет вашу камеру у собеседников; по окончании камера
возвращается сама.

**Записи созвонов** лежат на вкладке «Инструменты → Звонки» отдельным
списком. По нажатию на запись раскрывается **форма записи** (владелец,
2026-09-21): текст расшифровки и пять кнопок — «Скачать видеозапись»,
«Удалить видеозапись», «Транскрибировать», «Скачать транскрипцию», «Удалить
транскрипцию». «Удалить» стирает файл с сервера насовсем и переспрашивает:
другой копии нет, на телефоне запись не остаётся; вместе с видеозаписью
уходят её звуковые дорожки и текст. «Скачать» — это **отправка себе в чат с
ботом**, и подписано так нарочно: сохранить файл прямо из мини-приложения
Telegram не даёт вовсе, а из чата он открывается, пересылается и сохраняется
штатно. Бот отправляет документ не больше **50 МБ** (предел Bot API), а
сорок минут созвона весят под сотню — для таких записей кнопка называется
«Прислать ссылку на видеозапись», и в чат уходит ссылка на файл.
Транскрипция уходит в чат текстовым файлом.

Файлы — только у тех, кто состоит в модели: человек, которого позвали на один
созвон, хранилища на нашем диске не получает. Своё и чужое проверяется на
сервере — каталог выводится из подписи Telegram, а не из запроса, поэтому
знание чужого id не даёт ни прочитать запись, ни отправить, ни удалить.

**Запись** — сведённое видео со всеми участниками (300 кбит/с видео и
32 кбит/с звука, около 2,5 МБ в минуту) и, кроме него, **голос поканально**:
по звуковой дорожке на каждого участника — своя и каждого собеседника,
отдельным MediaRecorder (32 кбит/с). Дорожки уезжают на сервер следом за
видео файлами вида `track` с подписью (`X-Report-Meta`: к какой записи, чья,
с какой секунды началась); чья — сервер узнаёт при загрузке по псевдониму
звонка и подставляет имя из анкеты и username участника хранилища, гость по
ссылке остаётся с именем из своего «привета». Во вкладке звонков дорожек не
видно, и удаляются они вместе с видеозаписью. Предел файла — 100 МБ (около сорока минут): у предела
запись останавливается сама и сразу сохраняется — ничего не теряется. Файл
ложится в хранилище отчётов на сервере. nginx пропускает тело до 128 МБ
(пишется деплоем в `/etc/nginx/conf.d/system-dynamics-ui.conf`; раньше стоял
1 МБ по умолчанию, и загрузка отвечала 413).

**Диск.** Записи и файлы отчётов ложатся на диск сервера. Деплой печатает в
шаге «Подготовить сервер» строку «── диск ──» и предупреждает, когда занято
85 % и больше — тогда место надо освободить или расширить у хостера, иначе
следующая запись не сохранится.

**TURN ставится сам.** Деплой ставит coturn на этот же сервер, секрет рождает
и хранит в `.env` (`TURN_SECRET`), в браузер уезжают учётные данные на час.
Открывает порты 3478 и 49152–65535/udp, если включён ufw. Если у хостера свой
файрвол снаружи — откройте их там же. Внешний TURN тоже можно:
`TURN_URL/TURN_USER/TURN_PASS`.

**Как узнать, что TURN работает.** В итоге деплоя (Actions → запуск → Summary)
есть строка про TURN: «доступен снаружи» или «снаружи не отвечает». Проверяет
раннер GitHub — с самого сервера файрвол хостера не увидеть. Если не отвечает,
откройте шаг «Подготовить сервер» и строки после «── coturn ──»:

- «coturn слушает 3478» — на сервере всё в порядке, порт закрыт у хостера.
  Откройте в его панели 3478 tcp/udp и 49152–65535/udp и перезапустите деплой
  (Actions → CI/CD → Run workflow).
- «coturn НЕ ЗАПУЩЕН» или «порт 3478 не слушает» — ниже журнал coturn с
  причиной.
- «сервер за NAT … прописываю external-ip» — хостер отдаёт приватный адрес;
  деплой уже подставил публичный, ничего делать не нужно.

Камеру и микрофон спрашивает сам Telegram. На части клиентов (особенно старых
iOS) доступ из мини-приложения может быть недоступен — окно скажет об этом
словами, а не покажет чёрный экран.

## 6.7. Чаты групп: privacy mode и что хранит бот

Помощник отвечает «что решили в чате про X?» по сообщениям групп, где бот
состоит. Для этого нужно два условия, и оба — про доверие.

**1. У бота выключен privacy mode.** По умолчанию бот в группе получает
только команды и обращения к себе; всё остальное Telegram ему не показывает.
Выключается руками в @BotFather: `/setprivacy` → выбрать бота → **Disable**.
После смены режима бота надо **удалить из группы и добавить заново** —
иначе Telegram продолжит присылать ему только команды. Проверить: написать
в группе любое слово и посмотреть `ls ${DEPLOY_PATH}/data/chats` — появится
файл с id группы.

**2. Бот хранит ВСЕ сообщения групп, где он есть, — без срока.** Telegram
истории не отдаёт: бот видит только то, что пришло при нём, поэтому всё
увиденное ложится на диск сразу (`data/chats/<chat_id>.jsonl`), включая
правки (новая строка с тем же id; прежняя остаётся) и упоминания фото,
файлов и входов в чат словами. Это чужие разговоры, и участники группы
должны об этом знать: добавляя бота в группу, вы соглашаетесь, что её
переписка хранится на вашем сервере. Удалить чат из хранилища — удалить
его файлы; бот сам ничего не стирает.

**Кому что видно.** В контекст помощника чат попадает только у того, кто
состоит в группе прямо сейчас: перед каждым вопросом сервер спрашивает
Telegram (`getChatMember`) по каждому чату; выгнанный, вышедший и любая
ошибка проверки — «не состоит». Владелец модели исключением не является.
В контекст уходит не больше 20 000 знаков, новые сообщения важнее старых.

**Записи звонков** расшифровываются **по кнопке «Транскрибировать»** на
форме записи (владелец, 2026-09-21; при сохранении ничего не запускается)
моделью из строки «расшифровка записей звонков» настроек того, кто нажал
(Инструменты → Агенты, у ассистента; нужен провайдер вида «OpenAI» — сам
OpenAI или Groq с `whisper-large-v3-turbo`). Модель не выбрана — кнопка
отвечает словами, где её выбрать. Расшифровка идёт **по дорожкам**: каждая
уходит в `/audio/transcriptions` с `response_format: verbose_json`, куски
всех дорожек складываются по времени (плюс сдвиг дорожки того, кто
подключился позже), и перед каждой репликой стоит время и кто говорит —
имя из анкеты и `@username`: `[00:03] Иван @ivan: Здравствуй.` Записи без
дорожек (сделанные раньше) расшифровываются целиком, без имён. Идёт в фоне;
форма переспрашивает состояние раз в пять секунд (`GET
/api/reports/:id/transcript`), готовый текст показывает на форме, «Удалить
транскрипцию» стирает только текст. Текст лежит в
`data/calls/transcripts.json` и у встречи; удаление записи уносит и текст.

## 6.8. Сервис кодов: ключ, токены, план

Рядом с сервером стоит второе приложение — **сервис кодов** (`codes/`,
pm2-процесс `system-dynamics-codes`, порт `CODES_PORT`, по умолчанию 3010,
только localhost). Он один на всех и **всегда стоит на сервере
владельца**: код должен быть уникальным и неподделываемым, а это
возможно, только когда подписывает его один закрытый ключ.

Что он делает:

- при регистрации выдаёт **ключ** — постоянный, 160 бит, `XXXX-XXXX-…`
  (восемь групп). Ключ человек сохраняет: с ним он входит с любого
  Telegram-аккаунта. На диске лежит только хэш ключа;
- по ключу выдаёт **токен** — подписанную Ed25519 записку `{uid, plan,
  exp}` на час. Приложение обновляет его само и кладёт в каждый запрос
  заголовком `X-User-Token`;
- хранит **план** (`free`, `pro`, `max`) и запись о платеже. Оплата пока
  замокана: способ выбирается (USDT на TON, TON, Telegram Stars), платёж
  считается полученным сразу;
- отдаёт открытый ключ (`/public-key`) и список отозванных (`/revoked`).

Сервер хранилища проверяет токены **офлайн**: по открытому ключу сервиса,
который берёт один раз и держит в памяти; список отозванных обновляет раз
в минуту. Без годного токена сервер не отвечает (401 `needsCode`), кроме
`/api/org/me` — он говорит приложению, что ключ надо получить. Сервис
выведен наружу самим сервером под `/api/codes/…` (регистрация, токен,
план, замена ключа, открытый ключ) — nginx и HTTPS одни на всех.

Код (`uid`) привязывается к записи человека при первом входе с ним
(`data/org/identity.json`): у тех, кто уже был в системе, — к их
Telegram-id, поэтому владелец после регистрации ключа остаётся владельцем
со всеми данными.

Переменные `.env`: `CODES_URL` (задан — сервис включён), `CODES_DIR`,
`CODES_PORT`. Локально без `CODES_URL` кодов нет, и всё работает по одному
Telegram, как прежде.

### 6.8.1. Подписки, оплата и админ-бот

Сервис кодов — ещё и биллинг (`codes/src/billing.js`):

- **планы** правит владелец: название, стоимость в долларах, срок в
  днях и **вкладки** — галочками, какие разделы приложения план
  открывает (вложенная, например «Звонки», тянет за собой «Инструменты»).
  Список вкладок кладётся в токен и приходит в приложение с ним; до
  выбора у плана вкладки по уровню (free / pro / max);
- **подписка** — план со сроком; истёк — план free. За 5, 3 и 1 день до
  конца основной бот присылает напоминание (по одному разу на срок);
- **оплата**: Telegram Stars (инвойс выписывает основной бот, курс
  «звёзд за доллар» задаёт владелец), TON и USDT (jetton на TON) —
  перевод на кошелёк владельца с комментарием; кошельков у валюты может
  быть несколько, при оплате берётся случайный. Платёж в цепочке
  проверяется раз в полминуты через открытый API toncenter: комментарий
  перевода читается из BOC (`codes/src/boc.js`), сумма — не меньше
  нужной. Без ключа toncenter пускает около запроса в секунду — сервис
  ходит по одному и повторяет после 429; ключ `TONCENTER_API_KEY`
  снимает лимит. Курс TON — CoinGecko. Ожидающий платёж живёт сутки;
- **о каждой оплате** владелец получает сообщение от админ-бота.

**Админ-бот** — отдельный бот (@BotFather → новый бот). Его токен
владелец присылает ОСНОВНОМУ боту командой `/adminbot 123456:токен`;
сервер кладёт токен в `.env` (`ADMIN_BOT_TOKEN`), деплой его сохраняет,
сервис кодов подхватывает в течение минуты. Второй путь — секрет Actions
`ADMIN_BOT_TOKEN`. После этого: открыть админ-бота, нажать `/start` —
придёт кнопка «Открыть панель» (мини-приложение `https://<домен>/admin/`,
страница `codes/public/admin.html`, API `/api/admin/*`; подпись —
админ-бота, вход только владельцу по `OWNER_TELEGRAM_ID`). Чтобы
уведомления доходили, владелец должен хотя бы раз написать админ-боту.

Панель — три вкладки в одну строку (владелец, 2026-09-21): **Участники**
(первой — форма «выдать подписку»: @username или id — сервис сам понимает,
что прислали; план, стоимость, срок; ниже — кто, план, стоимость, полоса
остатка дней, код, «Отменить подписку» и «Удалить участника» в два касания:
ключ отзывается насовсем, uid уходит в список отозванных, и выданный ранее
токен гаснет), **Планы** (название, стоимость, срок, вкладки галочками;
применить/удалить; «Добавить» — «новый план»), **Способы оплаты** (Telegram
Stars с курсом; кошельки TON и USDT: название, адрес, баланс по цепочке,
история платежей; «+ кошелёк»).

Файлы в `CODES_DIR`: `plans.json`, `wallets.json`, `payments.json`;
подписка человека — в `users.json`.

## 6.9. Личные хранилища

У каждого зарегистрированного — своё **хранилище**: организация (роли,
участники, договоры), модель, сценарии, ссылки на блоки, откаты
помощника. Прежняя модель — хранилище владельца (`main`, лежит там, где
лежала); хранилища остальных — под `storages/<id>` внутри тех же
каталогов. Каждое хранилище — самостоятельный набор каталогов, который
можно унести целиком (задел под децентрализацию).

Запрос идёт в своё хранилище по умолчанию; чужое выбирается заголовком
`X-Storage` и открыто только участнику (кроме входа: «кто я», роли с
договорами, регистрация, ссылка). Участником становятся по ссылке или
по договору — в том хранилище, где ссылку выдали. Напоминания и бот
находят задачу в любом из хранилищ человека.

В каждой модели два актива, которые нельзя удалить: «Владелец» (в нём
появляются услуги и задачи для других) и «Система» (рынок: все стрелки
наружу идут в неё).

Что общее, а не по хранилищам: расписания напоминаний, память и
настройки помощника, файлы отчётов, встречи, рынок услуг, сообщения об
ошибках, связь кода с записью.

**Чужие схемы.** Участник видит схемы хранилищ, куда его позвали, на
плакардах в окне своей схемы (имя владельца, «свернуть»; свёрнутые —
полосами внизу с «развернуть»): срез участника, без правки.

**Рынок между хранилищами.** Заказ помнит хранилище, где его оставили,
и роль соискателя из схемы заказчика. Сделка заводит задачу в хранилище
заказчика и делает исполнителя его участником с этой ролью (договор
роли — на подпись при входе). У исполнителя в своём хранилище появляется
приватная услуга (видна ему и заказчику) с функцией в активе «Владелец»
— то же при вступлении по ссылке. Услуги приватны по умолчанию.


### 6.10. Языки интерфейса и бота (владелец, 2026-09-21)

Язык выбирается в приложении: Анкета → шестерёнка (справа от карандаша)
→ «Настройки» → «язык». Русский, английский, китайский. Выбор кладётся в
анкету (`lang`) и в `localStorage` (`sd_lang`); страница перезагружается,
чтобы всё переключилось разом. Бот читает язык из `data/org/langs.json`
(`server/src/lib/i18n.js`, пишется из `orgStore.setProfile`) и переводит
**всё исходящее** в `telegram.js`: текст и подписи кнопок — построчно,
точным совпадением, по шаблону с «{n}» или склейкой из кусков.

Словари — `locales/en.json` и `locales/zh.json` в корне репозитория, одни
на приложение и сервер: «русская строка → перевод». Русский — исходный
текст в коде, он же ключ; строку, которой нет в словаре (или перевод
пустой), приложение показывает по-русски. В деплой `locales/` едет рядом
с сервером (`deploy_pkg/locales`), сервер ищет их в `../../../locales` от
`src/lib` или в `LOCALES_DIR`.

Приложение ничего не вписывает руками: плагин сборки `web/i18n-babel.js`
(через `@vitejs/plugin-react`) оборачивает текст в JSX вызовами `t`/`tx`
из `web/src/i18n/t.js` — текст между тегами, строки-атрибуты, выражения
и шаблоны с подстановками. Поэтому на русском всё как было, а тесты по
русским подписям не меняются.

Добавить язык: файл `locales/<код>.json` (можно скопировать `en.json`),
строка в `LANGS` в `web/src/i18n/t.js` и в `server/src/lib/i18n.js`,
импорт файла в `t.js`. Обновить ключи после правок кода — из корня:

```bash
node scripts/i18n-extract.mjs      # locales/keys.json + недостающие ключи в en/zh пустыми
```

Заполнить переводы — партией через `python3 scripts/i18n-put.py`
(`{"ключ": ["en", "zh"]}` на stdin). Пустой перевод = «остаётся
по-русски»: так нарочно оставлены служебные строки (журнал сервера,
подсказки модели, регулярные выражения, словарные основы для поиска).

## 7. Где лежат данные

Всё, что стоит переносить и беречь, — под `${DEPLOY_PATH}/data`. Каталог
`app/` деплой перезаписывает целиком, `data/` — не трогает.

```
${DEPLOY_PATH}/data/scenarios/<telegram_user_id>/manifest.json   — список сценариев
${DEPLOY_PATH}/data/scenarios/<telegram_user_id>/<uuid>.json     — сами сценарии
${DEPLOY_PATH}/data/reports/users/<telegram_user_id>             — указатель на scope
${DEPLOY_PATH}/data/reports/<scope>/manifest.json                — список файлов
```

Комнаты созвонов на диск не пишутся вовсе: сигналы живут в памяти и
стираются через десять минут после звонка — в них адреса участников.

Имена файлов — сгенерированные сервером UUID, поэтому произвольный ввод в
URL не даёт доступа за пределы каталога пользователя.

Каталог отчётов назван не id пользователя, а случайным 32-символьным
`scope`, потому что ссылка на файл должна открываться браузером напрямую:
`<img src>` и обычная ссылка не могут подставить заголовок с подписью
Telegram. Знание пары `scope`+`id` и есть право на чтение — **у кого ссылка,
тот и прочитает файл**, а значит, отдать сценарий целиком значит отдать и
его отчёты. Загрузка и удаление подпись по-прежнему требуют. Указатель
`users/<id>` выдаётся один раз и от токена бота не зависит: сменится бот —
ссылки в уже сохранённых сценариях продолжат работать.

Каталог `data/` лежит **вне** `app/`, который стирается `rsync --delete`
при каждом деплое, поэтому обновление приложения файлы не трогает.
